# Initialize a product from this template

> Read AGENTS.md, START_NEW_SAAS.md, ARCHITECTURE.md, SECURITY.md and BILLING.md, plus relevant installed Next.js guides. Reuse the existing infrastructure. First collect the product name, unique slug, description, brand color, production hostname and GitHub owner/repository. Run `pnpm setup` interactively or `pnpm setup -- --name ...` with these values; do not hand-copy secrets or duplicate the setup logic. Review saas.config.json and branding. Existing env files must be preserved: never rotate credentials or delete volumes just to rerun initialization. If domain/ports change, explicitly reconcile the preserved non-secret env settings. Use `pnpm local:up` and `pnpm local:migrate` for full Docker local development. Put product behavior in the existing feature boundaries and replace legal placeholders only with reviewed policies. Do not invent payment success, testimonials or compliance. Configure real services separately, without committing credentials. Read the actual GitHub repository plan/visibility and protection capabilities before choosing protected deployments; otherwise use explicit allowlisted manual deployment. Never claim that environment naming alone enforces approval. Keep first VPS provisioning separate from routine app releases, preserve central Caddy, use unique Compose/proxy identities and immutable GHCR digests. Do not touch a live server without authorization. Verify setup idempotency, tests, workflow syntax, ARM64 build, migration runner and health where possible; report GitHub/provider/VPS checks as NOT VERIFIED when unavailable.

Owner: use GitHub's template feature, configure branch protections where supported, and select deployment mode deliberately. Customize prices, support contact, legal text and the first product feature. The template stores no shared production credentials; setup-generated secret bundles belong only to their product. Read START_NEW_SAAS.md for first deployment, normal releases, rollback and failure recovery.
